# レビューと公開前チェック

本文ができた後に使う。1人(1つのAI)で行うため、視点を切り替えて一つずつ読み直す。書いた直後に評価すると甘くなるので、各視点で本文を頭から読み、該当箇所を短く引用して指摘する。

レビューでは書き直さない。違和感とその理由だけを出し、直すのは本文側が行う。

## 目次

- 視点A:実務の読者として読む
- 視点B:事実を確認する
- 視点C:安全性を確認する
- 視点D:トーンを確認する
- 統合:直す順番を決める
- 簡易チェック(AIらしさ)
- 公開前チェックリスト
- 再レビューの基準

## 視点A:実務の読者として読む

準備で決めた読者の立場になる。記事を「自分の実務に置き換えられるか」という視点で、上から読む。購入検討者としてではなく、同じ作業で困っている人として読む。

挙げる項目(該当箇所の引用つき):

1. 困りごとの入口が、自分の状況とつながるか
2. 製品名や機能の説明が先行し、作業の場面が見えなくなる箇所
3. 実際に何をしたのかが曖昧な箇所
4. 下書き・実装・本番反映・自動運用の段階が混ざっている箇所
5. 実行前の確認、人の承認、戻し方、実行後の検証が足りない箇所
6. 自分の環境へ置き換えるために足りない前提
7. 最初に試せる低リスクな作業がわかるか
8. 再現プロンプトを、そのまま安全に使えるか

出力の形:

```markdown
### 実務の読者として読む
- 読者の状態(仕事 / 止まっている作業 / 不安):
- 自分ごとになる入口: [引用] → [理由]
- 実行内容が曖昧な箇所: [引用] → [理由]
- 安全境界が不足する箇所: [引用] → [理由]
- 置き換えに足りない前提: [引用] → [理由]
- 再現プロンプトの実行可能性と不足:
- 読後に最初に試せること:
```

## 視点B:事実を確認する

本文から確認が必要な記述を抜き出し、判定する。推測で「正確」としない。

- 外部サービス・ツールの現在の機能、対応環境、権限、制限
- 記事で行った操作と、実際に確認できた到達段階
- 「下書き作成」「実装」「本番反映」「自動運用」の区別
- 数字、件数、期間、成果、エラー内容(書き手が渡した記録と一致しているか)
- 実行前の承認、戻し方、実行後の検証の有無
- 公式情報の確認日と参考リンク

判定:

- 正確:資料または書き手の記録で確認できた
- 要修正:不正確、または誤解を招く
- 要確認:現時点では確認できない(書き手に質問する)

記録にない作業や成果が本文に入っていないかも、ここで確認する。見つけたら削るか質問に変える。

## 視点C:安全性を確認する

読者が記事やプロンプトを真似したときに、取り返しのつかない結果にならないかを見る。

- 強制上書き、公開、送信、削除、課金につながる操作に、事前の確認と承認がある
- 原本のバックアップ、または戻し方がある
- 実行後に結果を読み戻して検証する手順がある
- 同じ操作が二重に実行されないか(重複送信、重複登録など)
- APIキー、トークン、署名用のシークレット、認証ファイルが、本文・画像・プロンプトに含まれていない。読者に貼らせる設計にもなっていない
- Webhookや外部APIの応答の扱いが、書かれた範囲で安全か
- スクリーンショットに個人情報、顧客情報、未公開情報が写っていない

## 視点D:トーンを確認する

- 製品の万能感、成果の誇張がない
- 「絶対」「誰でも」「必ず」のような言い切りがない
- 読者が安全に試せる範囲がわかる
- 説教、煽り、情報商材風の語りになっていない
- 失敗、限界、人が判断する箇所が書かれている
- 優劣ではなく、前提や使い方の違いとして比較している
- 体験談として「〜と感じました」で着地できている箇所があるか。機能紹介の羅列になっていないか

## 統合:直す順番を決める

指摘を重複でまとめ、次の優先順で並べる。

1. 安全性(認証情報の露出、取り返しのつかない操作)
2. 事実の誤り、記録にない成果
3. 「実装」「検証」「未検証」の混在
4. 読者の不安が残る箇所
5. トーンの逸脱
6. 表記ゆれ

指摘が矛盾する場合は、どちらを優先したか理由を一言添える。反映しない指摘は「保留」として残す。

## 簡易チェック(AIらしさ)

`yomiyasu` が使えない場合の代替。次に当てはまる箇所を探して直す。コードブロックや再現プロンプトの中身は対象外。

- 人でも組織でもないものが主語で、比喩的な動詞を取っている(「〜が壊れる」「〜が効く」など)。誰が何をしたかに戻す
- 「重要なのは〜」のような前置き、「〜ではなく〜」の否定対比の多用
- 絵文字、文末のコロン、意味のない太字、箇条書きの乱用
- 補足のカッコが多い。英単語の前後に不要な半角空白がある
- 「これ」「両者」「片方」など、指す先が遠い指示語
- 同じ意味を言葉を変えて繰り返している段落
- 1文が長く、読点が3つ以上ある

直した後は、手順・数値・成果の大きさが変わっていないか確認する。

## 公開前チェックリスト

### 一次情報と事実

- [ ] 実際の作業、データ、設定、ログ、画面、失敗、検証結果のいずれかが入っている
- [ ] AIが作業結果や成果を作っていない
- [ ] 数字の出典または確認元がわかる
- [ ] 外部サービス名・機能名・手順が、現在の公式情報と一致している(確認日を記録した)
- [ ] 画像やスクリーンショットに個人情報・認証情報・未公開情報がない

### 設計

- [ ] 読者が、実務上の困りごと・止まっている作業・不安で定義されている
- [ ] 冒頭が2段落で、「具体的な困りごと → この記事で見せる実例」の順になっている
- [ ] 最低1例について「困りごと → 対象 → 依頼 → 実行前の確認 → 人の承認 → 結果 → 実行後の検証」が追える
- [ ] 「実装した」「検証した」「未検証」が区別されている
- [ ] 便利だった点だけでなく、失敗・限界・人が判断する箇所が書かれている
- [ ] 読者が最初に試せる、低リスクな一歩がわかる
- [ ] タイトルは35文字以内で、最初の9文字で入口が見える

### 再現プロンプトと参考リンク

- [ ] `## このプロンプトをそのままコピーして使えます` が、本文の締めの後にある
- [ ] プロンプトが、記事で実際に行った内容と一致している
- [ ] 対象ファイル・フォルダ・期間・件数を指定できる
- [ ] 原本を変更しない方法、または戻し方がある
- [ ] 変更・公開・送信・削除の前に、承認を求める指示がある
- [ ] 実行後に結果を読み戻して検証する指示がある
- [ ] 個人情報・認証情報・未公開情報の扱いが書かれている
- [ ] `## 参考リンク・出典` が、プロンプトの後にある。公式情報を優先している

### 文章

- [ ] 万能感、根拠のない成果表現、比較優位表現がない
- [ ] 「〜すべき」「〜しなければいけません」を不用意に使っていない
- [ ] 専門用語を、読者に必要な範囲で言い換えている
- [ ] AIらしさの除去工程を通し、そのあと手順・数値・成果の大きさを確認した

### 投稿

- [ ] noteに貼る範囲(タイトル、本文、再現プロンプト、参考リンク)から、管理用の情報を除いてある
- [ ] 導入文の直後に、noteの目次機能で目次を1つ入れた。手入力の目次を作っていない
- [ ] 目次の対象が実際の見出しと一致している
- [ ] 貼り付け後、空ブロックや見出しの崩れがない

## 再レビューの基準

| 変更内容 | やり直す視点 |
|---|---|
| 語尾、表記、軽微な調整 | トーンのみ、または不要 |
| 構成や順番の変更 | 実務の読者として読む、トーン |
| 数字・機能・手順に関わる追記 | 事実の確認 |
| 操作や公開、認証に関わる追記 | 安全性 |
| 大幅な全面修正 | すべて |
