# note記事を書く(ノウハウ・実務記録)

実際にやったことを、体験談として書く。「正解を教える手順書」ではなく、「自分もこう困っていた」「実際にこう使った」「ここまでは便利だった」「ここは注意が必要だった」という流れで、読者が自分の作業に置き換えられる材料を渡す。

## 前提:作業の中身は書き手の実績から取る

ノウハウ記事の価値は、実際に行った作業、実際のデータ、実際の失敗にある。AIが想像で補うと、動かない手順や起きていない成果が混ざり、読者が真似て損をする。

- 作業内容・数字・エラー・結果は、書き手が渡したログ、設定、画面、メモに書かれている範囲だけを使う
- 渡された資料から確認できないことは、「未検証」として分けて書くか、書き手に質問する
- 成果は確認できた大きさのまま書く。数字が少ないときは断定しない

## 利用者への話し方

このスキルを使うのは、ITや文章づくりに詳しくない書き手かもしれない。そのため、利用者に向ける言葉は、日常の言葉に直す。この文書の中の用語は、AIが内部で使う呼び名にとどめる。

| 内部の呼び名 | 利用者に話すとき |
|---|---|
| 一次情報 | 実際にやったこと、うまくいかなかったこと |
| 読者像 / ペルソナ | 読んでほしい人 |
| 6ステップ / ステップ5 | 「記事の設計メモ」「読む人の目で読み直してみました」 |
| 実装 / 検証 / 未検証 | 「作った」「動くのを確かめた」「まだ確かめていない」 |
| 再現プロンプト | 「読んだ人がそのままAIに貼れる依頼文」 |
| 視点A・B・C・D(レビュー) | 「読む人の気持ち」「事実」「安全面」「言い方」の確認 |
| yomiyasu / 簡易チェック | 「不自然な日本語を直す仕上げ」 |

進め方の説明も、長くしない。「まず少し質問させてください。そのあと設計メモを見ていただいて、OKなら書きます」程度で十分。

## 進め方

```
質問 → 設計メモ(6ステップ) → 見せて確認 → タイトル → 本文 → 依頼文・参考リンク → 読み直し → 不自然な日本語の仕上げ → 仕上げ
```

## 準備:質問は1〜2問ずつ

一度にたくさん聞くと、答えるのが負担になり、途中でやめてしまう人が多い。質問は1〜2問ずつ、会話の流れで聞く。前の答えから分かることは、聞き直さない。聞きたいことは次のとおり。資料(画面の写真、メモ、やり取りの記録)は、貼ってもらえば足りる。

- どんな作業の話か(対象、使ったツール、期間)
- 実際にやったことの記録(作業ログ、設定、スクリプト、画面、数字、失敗した点)
- どこまで確認できたか(作った / 動かした / 本番に反映した / 続けて使っている)
- 自分で確認・OKを出した箇所と、AIやツールに任せた箇所
- 読んでほしい人は誰で、どの作業で止まっているか(下の「読者の決め方」参照)
- 変化の速い外部サービスを扱うなら、公式情報の確認日

答えが短くて材料が足りないときは、「そのとき、画面にはどう出ましたか」「うまくいかなかったのはどこでしたか」のように、思い出しやすい問いで掘り下げる。答えるのが難しそうなら、選択肢を出して選んでもらう。

### 読者の決め方

購買者像ではなく、実務の状況で定義する。書き手が読者像を持っていればそれを使い、なければ次を聞くか、候補を出して選んでもらう。AIが一方的に決めない。

- 何の仕事をしているか
- どの作業で止まっている、または負担を感じているか
- すでに何を試したか
- 何が不安で実行できないか
- 読んだ後、最初に何を安全に試せるとよいか

例:「AIには相談しているが、回答をファイルへ移して実行するところで止まっている個人事業主」「広告の数字は見ているが、計測の問題と成果の低下を切り分けられず、変更をためらっている人」「複数商品のCSV更新が必要だが、元に戻せなくなるのが不安で手作業を続けている人」。

## 6ステップ

| # | ステップ | ノウハウ記事での意味 | 誰が出す |
|---|---|---|---|
| 1 | 伝えたいこと | 読後に読者が「自分の作業にどう置き換えられるか」「どこまで安全に試せるか」がわかる状態を1行で | 書き手と確認 |
| 2 | ポイント | 記事で見せる要素を3〜5個(困りごと、やったこと、便利だった点、注意点など) | 書き手(AIは案を出してよい) |
| 3 | 理由・背景 | 各ポイントの裏づけ。実際の作業、データ、設定、ログ、失敗、検証結果。ここが空だと一般論になる | 書き手(必ず聞く) |
| 4 | 伝えたい人 | 準備で決めた読者を、実務の状況で書く | 書き手と確認 |
| 5 | 補足・フォロー | 1〜3を読者の目線で読み直し、前提不足、専門用語、不安を見つける | AI |
| 6 | 順番 | 読者が自分の作業に置き換えやすい順に並べる | AI(理由つきで提示) |

### ステップ5の問い

- どこで「自分の仕事には関係ない」と感じるか
- どの専門用語・ツール名が説明なしで出てきているか
- 自分の環境で試すとき、何が足りない前提か
- どこで「失敗したら戻せないのでは」と不安になるか
- どこが誇張や万能感に見えるか

## 一次情報の確認

本文を書く前に、材料が揃っているか確認する。

- 実際に行った作業と、その前後の状態
- 使ったデータ、設定、スクリプト、画面、ログ
- 失敗、エラー、迷った判断、やり直した点
- 変更前に確認したこと、人が承認したこと
- 実行後に読み戻して検証した結果
- 外部サービスの現在の公式仕様(確認日とあわせて)

### 「実装した」「検証した」「未検証」を分ける

外部サービスや自動化を扱う記事は、次の3つを混ぜない。読者が「どこまで本当に動いたのか」を判断できなくなる。

1. 実装したこと:コードや設定を作った段階
2. 検証したこと:実行、読み戻し、ログ、画面などで確認できた段階
3. 未検証のこと:本番反映、継続運用、原因の確定など、まだ確認できていない段階

数字の異常を扱うときは、「画面上の設定」「イベントの発火」「集計された指標」「本番データ」を分けて原因を切り分ける。設定を変えただけで原因が確定したと書かず、変更前後のデータで確認できた範囲までを結果として書く。

### 「どう作ったか」が主題の記事

読者が自分でも同じようなサービスを作りたい場合は、設計の教訓だけを並べない。履歴やログで確認できる範囲で、次が追える本文にする。

1. コードを書く前に用意したもの(業務の流れ、入力と出力、最初に対応する対象一つの条件、状態の管理、外部サービスと認証と保存先)
2. 最初の動作版で、どこからどこまでを一本につないだか
3. 実際の実装順と、各工程の入力・出力・合格条件
4. 使ってみて見つかった問題と、その後の修正
5. 読者が対象一つ・入力一つ・出力一つで始める最小のルート

実際に行った順番を確認できない場合は、現在の構成から推測した順番を「実際の順番」として書かず、「これから作るならこの順で進める」という提案として分ける。

## タイトル:5案

- 25文字以内を目標、最大35文字
- 困りごと・行った作業・得られた結果のどれかが入る
- 最初の9文字で何の話かが見える
- 「〇〇の完全ガイド」「誰でも〜」のような情報商材風、煽りは避ける

## 本文

書く前に `references/writing-principles.md` を読む。

### 冒頭は2段落

長い要約や技術説明から始めない。読者が自分の作業場面を思い浮かべてから、この記事で何が見られるかへ進む。

1. 読者が日常的に行っている具体的な作業と、そこで生じる負担・迷い
2. この記事で紹介する実例、準備したもの、AIに任せた範囲、人が確認した範囲を、一文から数文で

タイトルの言い換え、本文の長い要約、「この記事では」を重ねた説明、手順に入る前の長い注意書きは冒頭へ詰め込まない。

例(固定文にせず、記事ごとの場面に置き換える):

> 請求書の金額を、メールの添付からスプレッドシートへ手で写す。月末にまとめてやると、思った以上に時間がかかります。
>
> この記事では、AIアシスタントを使って、この転記を半自動にした実例を紹介します。どんな準備をして、どこをAIに任せ、どこを自分で確認したのかをまとめました。

### 基本の流れ

```
冒頭       読者の具体的な困りごと → この記事で見せる実例
私自身     自分も同じように後回しにしていた、迷っていたことを書く
今回やったこと  相談ではなく、実際に行った作業、確認した数字、変更した内容
便利だった点    機能名ではなく、作業の場面で何が楽になったか
注意点     AIに丸投げしない箇所、事前確認が要る操作、数字が少ないときは断定しない
余韻       同じように困っている人の参考になれば、という形で締める
再現プロンプト  読者が自分の環境に置き換えられる詳細な依頼文
参考リンク・出典  本文で触れた公式ドキュメントや根拠ページ
```

### 文体の基準

- 「できます」「おすすめです」で押し切らず、「〜と感じました」「〜ではないかと思います」で体験談として着地させる
- 機能説明より先に、読者の作業場面を置く
- すごさの誇張ではなく、気持ちの重さが減った、確認が進んだ、判断しやすくなった、という実感を書く
- 実行した内容は具体的に書き、成果は大きく見せすぎない
- 比較対象がある場合は優劣ではなく、前提や使い方の違いとして書く
- 専門用語は、読者に必要な範囲で言い換える

## 再現プロンプト

本文の締めの後に置く。読者が自分の環境へそのまま持っていけるようにする。見出しは `## このプロンプトをそのままコピーして使えます`。含めるもの:

- 目的
- 前提データ(対象のファイル・フォルダ・期間・件数を指定できる欄)
- 確認してほしい項目
- 原本を変更しない方法、または戻し方
- 変更・公開・送信・削除の前に、人の承認を求める指示
- 実行後に結果を読み戻して検証する指示
- 個人情報・認証情報の扱い
- スマホでも読める要約を出す指示

記事で実際に行った内容と、プロンプトの内容を一致させる。

## 参考リンク・出典

見出しは `## 参考リンク・出典`。再現プロンプトの後に置く。公式ドキュメントなど一次情報を優先し、変化の速いサービスは確認日を添える。

## 安全面の扱い

次を扱う記事は、安全条件を本文と再現プロンプトの両方に入れる。

- 強制上書き、公開、送信、削除、課金につながる操作
- 認証情報、Webhook、外部API

基本は「対象・差分・承認・バックアップ・実行後の読み戻し」。APIキー、トークン、署名用のシークレット、認証ファイルは、記事にもプロンプトにも貼らない。読者に貼らせる設計にもしない。

## 読み直し

`references/review.md` の手順で、読む人の実務・事実・安全面・言い方の4つの目から順に読み直す。直した点は、利用者には「ここを直しました」と短く伝えるだけにする。

## 不自然な日本語の仕上げ

読み直しで内容が固まったら、最後に不自然な日本語を取る。

1. 利用可能なスキル一覧に `yomiyasu`(`note-writing-skills:yomiyasu` のように接頭辞がつく場合も含む)があれば、それで本文を推敲する。コードブロックや依頼文の中身は書き換えさせない。利用者には、推敲した本文だけを見せる(変換の理由の一覧は出さない)
2. 無ければ、利用者に何も求めず、`references/review.md` の「簡易チェック」で同じ作業を自分で行う。導入の案内や説明をして足止めしない
3. 推敲のあとで、成果の大きさや確信度が変わっていないか、手順や数値が変わっていないかを確認する

## 仕上げ

`references/review.md` の公開前チェックを内部で通し、利用者には「ここは確認してください」という点だけを短く伝える。noteに貼る範囲(タイトル、本文、依頼文、参考リンク)は、コピーしやすいように1か所にまとめて渡す。noteへの貼り付けでは、導入文の直後にnoteの目次機能で目次を1つ入れ、手入力の目次は作らない。空行を連打して余白を作らない(空ブロックができるため)。ファイルへの保存は、書き手が望んだときだけにする。
