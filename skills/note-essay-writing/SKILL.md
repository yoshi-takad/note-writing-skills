# note記事を書く(エッセイ・想い・制作背景)

書き手の経験と考えを、読者が自分のペースで受け取れる文章にする。教え込む文章ではなく、隣に座って静かに話す文章を目指す。

## 前提:AIは書き手の経験を持たない

この種の記事は、書き手が実際に体験し、実際に考えたことが中身になる。AIが出来事、感情、きっかけを補って書くと、読みやすくても他人の文章になり、書き手の名前で公開する記事として危うい。だから次を守る。

- 体験・感情・出来事・会話は、書き手が話した範囲だけを使う。足りないときは「足りない」と伝えて質問する
- 補う案は「こういう経験はありますか?」と問いの形で出す。確認前の案を本文に入れない
- 書き手が「そう思う」と言ったことを、一般的な事実や断定に変えない

## 利用者への話し方

このスキルを使うのは、文章づくりやAIに詳しくない書き手かもしれない。そのため、利用者に向ける言葉は、日常の言葉に直す。この文書の中の用語は、AIが内部で使う呼び名にとどめる。

| 内部の呼び名 | 利用者に話すとき |
|---|---|
| 一次情報 | 実際にあったこと、そのとき思ったこと |
| ペルソナ / 読者像 | 読んでほしい人 |
| 6ステップ / ステップ5 | 「記事の設計メモ」「読む人の目で読み直してみました」 |
| 視点A・B・C(レビュー) | 「読む人の気持ちで」「事実に間違いがないか」「言い方が強すぎないか」の確認 |
| yomiyasu / 簡易チェック | 「不自然な日本語を直す仕上げ」 |

進め方の説明も、長くしない。「まず少し質問させてください。そのあと設計メモを見ていただいて、OKなら書きます」程度で十分。

## 進め方

```
質問 → 設計メモ(6ステップ) → 見せて確認 → タイトル → 本文 → 読み直し → 不自然な日本語の仕上げ → 仕上げ
```

本文に入る前に、必ず設計メモの要点を書き手に見せて確認をもらう。ここがずれたまま本文まで進むと、直しが全体に及ぶ。

## 準備:質問は1〜2問ずつ

一度にたくさん聞くと、答えるのが負担になり、途中でやめてしまう人が多い。質問は1〜2問ずつ、会話の流れで聞く。前の答えから分かることは、聞き直さない。聞きたいことは次のとおり。

- テーマと記事の種類(想い・価値観/素材や技法/作品やサービスのコンセプト/制作背景/お客様との接点)
- 読んだ後に読者に何が残ってほしいか(1行)
- 読んでほしい人は誰で、今どんな場面・気持ちにいるか(下の「読者の決め方」参照)
- 実際にあったこと、そのとき思ったこと(一次情報)。写真、メモ、お客様の声などの素材があれば受け取る
- 表記ルール(ブランド名・商品名の書き方、一人称、避けたい表現)。指定がなければ一人称は書き手に確認する

答えが短くて材料が足りないときは、「そのとき、どんな気持ちでしたか」「きっかけは何でしたか」のように、思い出しやすい問いで掘り下げる。答えるのが難しそうなら、いくつか選択肢を出して選んでもらう。

### 読者の決め方

読者像は書き手によって違うため、AIが決めない。次の順で進める。

1. 書き手がペルソナ資料や読者像を持っているなら、それを受け取り、記事のテーマに最も重なるものを選んで確認する
2. 持っていなければ、「この記事を読んでほしいのは、どんな場面にいる人ですか」と聞く
3. 答えに迷う場合は、テーマと実際にあったことから、読む人の候補を2〜3個、場面の描写つきで出して選んでもらう

属性(「30代女性」など)で止めず、「今、〇〇している人」と場面と気持ちで書く。

## 6ステップ

| # | ステップ | やること | 誰が出す |
|---|---|---|---|
| 1 | 伝えたいこと | 読者に何が残ってほしいかを1行で。知識より、感じ方がどう変わるかで書く | 書き手 |
| 2 | ポイント | テーマを構成する切り口を3〜5個 | 書き手(AIは案を出してよい) |
| 3 | 理由・背景 | 各ポイントについて、なぜそう考えたか、どんな経験があったか。ここが空だと一般論になる | 書き手(必ず聞く) |
| 4 | 伝えたい人 | 準備で決めた読者を「今、〇〇な人」に変換する | 書き手と確認 |
| 5 | 補足・フォロー | ステップ1〜3を、4の読者の目線で読み直し、補うべきことを見つける | AI |
| 6 | 順番 | その読者が最もスムーズに理解できる並びを決める | AI(理由つきで提示) |

### ステップ5の問い

読者の目線で、次を一つずつ確認する。説明を増やすための工程ではなく、読者が最後まで「自分のことだ」と感じながら読めるようにするための工程。

- どこで「自分には関係ない」と感じるか
- どの言葉が抽象的すぎて意味が取れないか
- 書き手が当然と思っていて、読者は共有していない前提は何か
- どこで「でも自分は…」と引っかかるか
- どこが押しつけに感じられるか

出た補足は、本文の中に組み込む。

### ステップ6の考え方

情報の種類で並べず、「前の段落が次の段落を必要とする」因果の順に並べる。何があったのか → なぜそう考えたのか → 何を試したのか → 何が変わったのか。入口は、読者が最も理解しやすい具体的な地点(読者の場面、出来事、書き手の疑問、誰かの言葉など)から選ぶ。毎回同じ型に当てはめない。

## タイトル:5案

- 25文字以内を目標、最大35文字
- 最初の9文字で、何についての記事かが見える
- 作品・素材・読者の気持ちなど、具体的なものが一つは入る
- 煽らない。「〇〇について」「最近思ったこと」のような曖昧さも避ける
- 5案それぞれに、狙い(検索されたいのか、気持ちに触れたいのか)を一言添える

## 本文

書く前に `references/writing-principles.md` を読む。この文章の質は、そこにある判断軸で決まる。

流れの目安(型として固定しない。ステップ6で決めた順番を優先する):

```
読者の場面、または出来事から入る
→ その気持ちの影や矛盾(「でも」の部分)
→ 書き手自身の経験、迷い、気づき
→ 押しつけない形で考えを差し出す
→ 作品・素材・サービスとのつながり(書き手の判断の結果として自然に置く)
→ 余韻で終える(読者の選択や日常にそっと戻す)
```

すべての記事を「思想への着地」にする必要はない。制作記録なら判断と結果、お客様との出会いならその言葉の受け取り方、告知なら変更点と利用方法、というように、その記事の役割を終点にする。案内が必要なら行動を具体的に書き、選ぶかどうかは読者に委ねる。

出力は、会話の中にそのまま書いて渡す。ファイルへの保存は、書き手が望んだときか、作業フォルダが明らかにあるときだけにする。形式は `references/article-template.md` を参考に、利用者にはタイトルと本文を中心に見せる(設計メモは要点だけ)。

## 読み直し

本文ができたら `references/review.md` の手順で、読む人の気持ち・事実・言い方の3つの目から順に読み直す。AIが書いた文章をAIが評価するとどうしても甘くなるので、見方を切り替えて一つずつ、該当箇所を引用しながら進める。直すときは、書き手の声を保つ。直した点は、利用者には「ここを直しました」と短く伝えるだけにする。

## 不自然な日本語の仕上げ

読み直しで内容が固まったら、最後に不自然な日本語を取る。

1. 利用可能なスキル一覧に `yomiyasu`(`note-writing-skills:yomiyasu` のように接頭辞がつく場合も含む)があれば、それで本文を推敲する。利用者には、推敲した本文だけを見せる(変換の理由の一覧は出さない)
2. 無ければ、利用者に何も求めず、`references/review.md` の「簡易チェック」で同じ作業を自分で行う。導入の案内や説明をして足止めしない
3. どちらの場合も、推敲のあとで次を確認する。文章をなめらかにする過程で、書き手の確信度や出来事の大きさが変わりやすいため
   - 「〜と思う」が断定になっていないか
   - 出来事や感情が大きくなっていないか
   - 書き手の言い回しが消えて均質な文体になっていないか

## 仕上げ

`references/review.md` の公開前チェックを内部で通し、利用者には「ここは確認してください」という点だけを短く伝える。note本文として貼る範囲(タイトルと本文)は、コピーしやすいように1か所にまとめて渡す。noteへの貼り付けでは、目次はnoteの目次機能を使い、空行を連打して余白を作らない(空ブロックができるため)。
